Full database logical dump includes Auth rows, permissions, ledger and all schemas; pg_dumpall roles includes password verifiers. ## Provider ownership qualification (read-only source evidence)

Production initdb OID-10 role is supabase_admin (superuser). Vault/pg_trgm/plpgsql are owned by supabase_admin; pg_stat_statements/pgcrypto/uuid-ossp by nonsuperuser postgres. session_preload_libraries contains supautils; the privileged role is supabase_privileged_role, with supabase_admin as privileged extension installer. The runtime therefore uses the actual bootstrap name, a minimal official Supautils profile for the five installed extensions, and a complete partition of the native pg_restore TOC. Native pg_dump omits extension owners; --use-set-session-authorization alone cannot recover that information. Database and extension schemas are replayed once, real extensions are created at their recorded exact version using fresh local connections authenticated as their recorded owners, then every remaining native entry (including database properties/ACL and extension data) is restored with normal ALTER OWNER. Nothing is removed from the original archive. Coverage of every TOC id is asserted, and the entire catalog is compared afterward. The six source extension names/versions/schemas/owners are also pinned before capture. It does not claim to recreate all hosted service configuration. Extension owner is included in strict comparisons. The source provider contract and bootstrap identity must match before capture.

The complete original role dump remains encrypted and unchanged. Replay skips exactly one redundant CREATE ROLE supabase_admin because initdb already created that verified OID-10 role. All ALTER ROLE statements, password verifiers, settings and grants remain byte-preserved. Missing/duplicate creation or missing bootstrap SUPERUSER attributes stops replay. No fake managed-role attributes or --no-owner/--no-acl/--no-role-passwords are used. The synthetic provider rehearsal now includes a nonsuperuser postgres, privileged-role membership, trusted and privileged extensions, role-dump replay and source/target owner comparison. This is a changed qualification boundary, not a replay of old R33 tests.

SQL candidates in the restored database run as the actual nonsuperuser postgres using a new local psql connection authenticated as postgres, not an impersonated superuser session. Failure of that principal is a stop condition, with no escalation. Catalog comparisons and deliberate rollback-only tamper tests use the isolated bootstrap administrator. This does not alter any hosted role.

Before source export, capture also pins the accepted central seal definition SHA-256, owner, ACL, security-invoker attribute and search_path, the three M232 predecessor body hashes, safe API role attributes and absence of the new annual/C4/monthly contracts. Live read-only metadata matched these pins. A missing required seal is an error. After independent download/decryption the runner records only the encrypted archive SHA-256 and size, so recovery evidence survives a later chain failure. Source migrations still never execute on the hosted database. The restore readiness bound is 120 seconds, exceeding pg_ctl's own 60-second error timeout, with sanitized startup/state diagnostics on failure.

The mixed-owner qualification includes an auth-like schema owned by a NOLOGIN role without database CREATE permission. Restore therefore uses native ALTER OWNER for ordinary objects; it does not grant that role temporary CREATE privileges or elevate it. The documented pg_dumpall --database=postgres option selects its initial database; -d is a connection string for that utility and is not used as a plain database name. Source role dumps, original custom dump and captured extension metadata remain unchanged within the encrypted envelope.

Storage consistency also requires a fresh read-only metadata/version read after COMMIT to equal the object list captured in the database snapshot, in addition to downloading every object twice with identical SHA-256. Thus a metadata/version change between the snapshot and first byte read cannot pass merely because the two later byte reads happen to match. No source Storage writes occur.

Native TOC listing uses --list --create --verbose so the declared archive entry count must equal all listed unique ids. PostgreSQL forces DATABASE/DATABASE PROPERTIES in --create mode regardless of use-list; therefore database creation, properties, ACL, comments and security labels are partitioned into the first phase, and the remaining phase uses no --create. No duplicate CREATE DATABASE or skipped database ACL is tolerated. This behavior is grounded in upstream pg_backup_archiver.c, not an expected-fingerprint adjustment.
